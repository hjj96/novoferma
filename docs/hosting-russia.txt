Размещение: Amvera или Beget. Подготовлено 05.11.2026

Код не зависит от API одного хостинга. Сайт и /api/partner-requests обслуживаются
одним процессом; SQLite хранится отдельно от публичных файлов. В репозитории
есть Dockerfile и amvera.yaml. Это подготовка к размещению, а не факт деплоя:
Docker на текущем компьютере недоступен, сборка образа и облачный запуск ещё
не проверены. Локально проверяется сам Python-сервер и реальный путь заявки.

AMVERA

Официальная документация подтверждает Dockerfile, containerPort и отдельное
постоянное хранилище. amvera.yaml задаёт порт8080 и /data. Приложение пишет
в /data/private/requests.sqlite3, а не в пересоздаваемую папку кода /app.
Нужен российский регион размещения при создании проекта.

1. Собрать сайт и выполнить проверки по README до подключения репозитория.
2. В проекте указать NOVOFERMA_ORIGINS=https://ФАКТИЧЕСКИЙ-ДОМЕН без пути,
   query и финального слэша. При нескольких используемых доменах — список
   через запятую. Это точный список разрешённых Origin, не wildcard.
3. Проверить, что постоянный /data/private принадлежит UID/GID10001 и доступен
   только ему. Новый mount может иметь другие права, чем каталог образа:
   администратор должен подготовить эту выделенную подпапку до запуска.
   Не открывать права всей /data и не давать веб-доступ к ней.
4. Включить HTTPS на входе. Прокси должен сохранять Host, ограничивать размер
   тела, скорость запросов и тайм-ауты. Встроенный Python HTTP-сервер рассчитан
   на запуск за таким входом, а не на самостоятельную защиту от публичной нагрузки.
5. При первом запуске проверить реальную заявку, номер, чтение оператором,
   затем перезапуск/пересборку и сохранность той же записи. Назначить ответственного
   за просмотр входящих: автоматическая почта/CRM пока не подключена.

Один экземпляр сервиса с локальным persistent SQLite. Не включать несколько
реплик с независимыми томами: у них будут разные заявки. Для масштабирования
требуется общая транзакционная база и общий ограничитель запросов.

BEGET

Контейнер рассчитан на VPS/облако с Docker, постоянным диском и HTTPS-прокси.
Обычная загрузка HTML в shared-хостинг не запускает Python API. Если будет
выбран shared-тариф, сначала проверить поддержку постоянного процесса Python
или разместить приём отдельно с проксированием /api на том же домене.

Пример для администратора VPS после проверки образа:

docker build -t novoferma-site .
sudo install -d -m 700 -o 10001 -g 10001 /srv/novoferma/private
docker run -d --name novoferma-site --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  -v /srv/novoferma:/data \
  -e NOVOFERMA_ORIGINS=https://ФАКТИЧЕСКИЙ-ДОМЕН \
  novoferma-site

Перед этим указать реальный домен и настроить HTTPS-прокси на localhost8080. Контейнер использует общий предел
240 запросов/минуту; индивидуальные ограничения клиентов должен применять edge.
Без прокси CLI по умолчанию ограничивает каждый peer до12/минуту.
Файлы данных не включать в Git, Docker-образ, ZIP и папку сайта. Резервную
копию делать командой сервера backup, проверить восстановление и хранить
отдельно от рабочего диска; политика доступа/срока хранения задаётся владельцем.

На 05.11.2026 ссылка справки Beget перенаправила на официальное уведомление
о восстановлении после инцидента 1–2 ноября, обновлённое4 ноября. Поэтому
актуальная доступность продукта и ограничения должны быть проверены перед
выбором тарифа. Это не проверка состояния аккаунта пользователя.

ГРАНИЦЫ ГОТОВНОСТИ

До публичного запуска: фактический домен, постоянный том и его права,
HTTPS/edge limits, ответственный за заявки, резервное копирование/восстановление,
утверждённая информация об обработке данных и проверка на выбранном хостинге.
Платёжный тариф, договор, секреты почты/CRM и ресурсы облака не создавались.
